# Заметки к защите PulseChat

## Короткое вступление

> PulseChat — учебный модульный монолит для кейса №1 «Мессенджер». React использует REST для регистрации, списка, истории и поиска, а Socket.IO — для изменений в реальном времени. NestJS проверяет JWT, членство и роль; PostgreSQL хранит данные. Новое сообщение сначала сохраняется, затем доставляется всем участникам через их персональные комнаты `user:<userId>`, а отправитель получает ack. Повтор с тем же `clientMessageId` не создаёт вторую запись. В группах действуют роли OWNER, ADMIN и MEMBER. Решение намеренно не добавляет брокер, серверные read receipts и вложения: это границы MVP.

## Факты

- Пять таблиц: `users`, `chats`, `chat_members`, `messages`, `audit_logs`.
- Связь пользователей и чатов N:N хранится в `chat_members`; её ключ — `(chat_id, user_id)`.
- DIRECT объединяет ровно двух участников, его состав не изменяется.
- GROUP использует роли `OWNER`, `ADMIN`, `MEMBER`.
- История загружается вверх cursor-параметром `before`; поиск использует `ILIKE` внутри одного чата.
- Уникальность `(sender_id, client_message_id)` защищает повтор отправки.
- `user:<userId>` объединяет все вкладки и устройства пользователя. `chat:<chatId>` используется после `join_chat`/`leave_chat` и для контроля доступа, но не определяет получателей нового сообщения.
- `chat_list_changed` обновляет список чатов, `chat_details_changed` — название, состав или роль, `chat_access_revoked` удаляет чат из интерфейса и лишает доступа.
- Unread — локальный `Record<chatId, number>`: растёт для чужого сообщения в неактивном чате и очищается при его открытии. После reload может сброситься; server-side read receipt отсутствует.

## Вопросы и ответы

### Почему выбран модульный монолит?

Для обязательного MVP это минимальная объяснимая архитектура: один backend, одна транзакционная БД, REST и Socket.IO в одном процессе. Отдельный брокер оправдан только после измеренной нагрузки или необходимости масштабировать доставку между несколькими процессами.

### Почему PostgreSQL?

Нужны связи, ограничения, транзакции и индексы. PostgreSQL позволяет атомарно хранить сообщения, роли и уникальный `clientMessageId` без отдельной системы хранения.

### Почему Socket.IO, а не polling?

Socket.IO даёт двустороннее событие, handshake с JWT и серверный ack. Polling проще, но добавляет задержку и лишние запросы при появлении нового сообщения.

### Почему сообщение отправляется в `user:<userId>`, а не только в `chat:<chatId>`?

Пользователь должен увидеть новое сообщение и новый чат без открытия нужного диалога. Персональная комната доставляет событие всем его активным вкладкам; frontend обновляет preview, порядок sidebar и unread без reload.

### Как обеспечивается надёжность отправки?

Gateway сначала проверяет DTO и членство, затем `MessagesService` сохраняет запись в PostgreSQL. Только после записи `RealtimeRegistryService` публикует `message_created`, а отправитель получает ack.

### Что происходит при повторе запроса?

Клиент повторяет отправку с тем же `clientMessageId`. Уникальная пара `(sender_id, client_message_id)` возвращает существующее сообщение: второй INSERT и второй broadcast не выполняются.

### Как работают роли?

OWNER назначает и снимает ADMIN. OWNER и ADMIN добавляют MEMBER; ADMIN не может удалять ADMIN или OWNER. MEMBER может читать и отправлять сообщения, но не управляет составом. Проверка есть и в интерфейсе, и на backend.

### Чем unread отличается от read receipt?

Unread — только удобство текущего интерфейса и хранится в памяти frontend. Read receipt — серверное состояние о прочтении на каждого пользователя; оно потребовало бы отдельной модели и в MVP не реализовано.

### Почему нет Kafka, RabbitMQ и Redis?

Требования MVP не требуют их. Для одного backend-процесса персональные Socket.IO rooms достаточно просты. При горизонтальном масштабировании понадобятся adapter/брокер и анализ гарантий доставки.

### Как масштабировать поиск?

Сейчас используется `ILIKE`, достаточный для учебного малого объёма. При росте данных следующий шаг — PostgreSQL full-text search или `pg_trgm` после профилирования.

### Как проверена работа?

Backend-набор содержит 21 e2e/WebSocket-тест: auth, роли, история, поиск, идемпотентность и personal-room события. Отдельный Playwright-сценарий проверяет новый чат, unread и смену роли во втором браузерном контексте без reload. Конкретные даты и команды фиксируются в `docs/testing.md`.

## Честные ограничения

- access JWT без refresh-token;
- один backend-процесс без broker/Redis;
- `ILIKE` вместо полнотекстового поиска;
- локальный unread без server-side delivery/read receipts;
- вложения и объектное хранилище не входят в MVP;
- ориентир `<200 мс` не заявляется как SLA без отдельного измерения.
