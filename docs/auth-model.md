# Модель аутентификации и авторизации PulseChat

## 1. Область модели

PulseChat использует упрощённую модель только с access JWT. Refresh-токенов, серверных сессий, OAuth и внешнего провайдера идентификации в MVP нет. Это осознанное учебное ограничение: поток входа легко показать и объяснить, а обязательное требование презентации допускает вариант только с JWT.

Важно разделять два понятия:

- аутентификация отвечает на вопрос «кто выполняет запрос?»;
- авторизация отвечает на вопрос «имеет ли этот пользователь доступ к конкретному чату и действию?».

JWT подтверждает личность, но сам по себе не даёт доступ ко всем чатам. Членство и роль проверяются на сервере по `chat_members` при каждом защищённом действии.

## 2. Регистрация

Поток `POST /api/auth/register`:

1. `ValidationPipe` проверяет DTO: `username` после `trim` должен иметь длину 3-32 символа, пароль - 8-72 символа. Лишние поля запрещены.
2. `AuthService` вычисляет bcrypt-хэш. Число раундов задаёт `BCRYPT_ROUNDS`, значение по умолчанию для разработки - 12.
3. В `users.password_hash` сохраняется только хэш. Исходный пароль не пишется в БД, ответ и журнал.
4. Ограничение `UNIQUE users(username)` предотвращает повторное имя. Нарушение преобразуется в HTTP 409.
5. В `audit_logs` добавляется `USER_REGISTERED`.
6. Сервер выпускает access JWT и возвращает только `{ accessToken, user: { id, username } }`.

Bcrypt специально использует случайную соль внутри результата хэширования. Поэтому одинаковые пароли не обязаны иметь одинаковый хэш, а проверка выполняется через `bcrypt.compare`.

## 3. Вход и выпуск JWT

Поток `POST /api/auth/login`:

1. Пользователь ищется по точному `username`; только этот внутренний запрос явно добавляет скрытое поле `passwordHash`.
2. `bcrypt.compare` сравнивает введённый пароль с хэшем.
3. Для неизвестного пользователя и неверного пароля возвращается одинаковый HTTP 401, чтобы не раскрывать наличие учётной записи.
4. В журнал пишется `USER_LOGGED_IN` без пароля и JWT.
5. JWT подписывается секретом `JWT_SECRET` из окружения. Приложение не стартует, если секрет отсутствует или короче 32 символов.

Полезная нагрузка токена содержит:

```json
{
  "sub": "user UUID",
  "username": "andrey",
  "iat": 0,
  "exp": 0
}
```

`iat` и `exp` выставляет JWT-библиотека. Срок задаётся `JWT_EXPIRES_IN`; в Docker-конфигурации разработки используется `8h`. Это настраиваемое значение, а не обещание постоянной длительности сессии.

## 4. Защита REST API

Защищённый клиентский запрос содержит заголовок:

```http
Authorization: Bearer <access JWT>
```

`JwtAuthGuard` и `JwtStrategy` выполняют следующую цепочку:

1. извлекают Bearer-токен;
2. проверяют подпись и срок действия;
3. получают `sub`;
4. повторно находят пользователя в БД;
5. помещают безопасное представление `{ id, username }` в `request.user`.

Повторная проверка пользователя означает, что корректно подписанный токен удалённой учётной записи не принимается. После этого сервисы выполняют предметные проверки:

- список чатов выбирается только через членство текущего пользователя;
- открытие чата, история, поиск, `join_chat` и отправка требуют строку в `chat_members`;
- управление группой дополнительно проверяет `OWNER`, `ADMIN` или запрет для `MEMBER`;
- операции состава и названия запрещены для `DIRECT` независимо от роли.

## 5. WebSocket handshake

Socket.IO-клиент передаёт токен при установке соединения:

```ts
io(url, {
  auth: { token: accessToken },
});
```

Серверный middleware Gateway:

1. читает `socket.handshake.auth.token`;
2. проверяет JWT;
3. загружает пользователя;
4. записывает `{ id, username }` в `socket.data.user`;
5. отклоняет соединение при любой ошибке;
6. после подключения присоединяет сокет к персональной комнате `user:<userId>`.

Персональная комната нужна, например, чтобы удалить все активные соединения исключённого участника из `chat:<chatId>` и отправить ему `chat_access_revoked`.

Handshake не заменяет проверку доступа к конкретному чату. `join_chat` и `send_message` каждый раз вызывают `requireMembership`.

## 6. Почему `password_hash` не возвращается

Поле сущности `User.passwordHash` помечено `select: false`, поэтому обычные TypeORM-запросы его не выбирают. Сервис входа запрашивает поле явно и использует только для `bcrypt.compare`. Внешние ответы строятся вручную из `id` и `username`; сущность пользователя целиком наружу не сериализуется.

Это защита в глубину: даже случайное использование обычного репозитория не должно добавить хэш в JSON. Сам хэш тоже чувствителен, потому что его можно атаковать офлайн.

## 7. Хранение токена на клиенте

Для понятного учебного клиента access JWT хранится в `localStorage`. Axios interceptor добавляет Bearer-заголовок. При HTTP 401 клиент очищает локальную сессию; кнопка выхода делает то же самое.

Компромисс: `localStorage` доступен JavaScript-коду страницы, поэтому XSS может украсть токен. В production-системе следует рассмотреть строгую Content Security Policy, короткий access-токен и refresh-сессию в защищённой `HttpOnly Secure SameSite` cookie. Эти механизмы намеренно не добавлены в MVP.

## 8. Аудит

В `audit_logs` сохраняются значимые действия:

- регистрация;
- вход;
- создание группового чата;
- добавление участника;
- удаление участника;
- изменение роли.

Запись содержит актёра, действие, тип/идентификатор сущности, безопасные метаданные и время. Пароли и JWT не журналируются. `user_id` допускает `NULL` и использует `ON DELETE SET NULL`, чтобы история не терялась при удалении пользователя.

## 9. Контроли безопасности

| Риск | Контроль MVP |
|---|---|
| Пароль в открытом виде | bcrypt, `password_hash`, явный безопасный ответ |
| Подмена пользователя | проверка подписи и `exp` JWT |
| Доступ к чужому чату | серверная проверка `chat_members` |
| Повышение роли MEMBER | изменение ролей разрешено только OWNER; роль OWNER через endpoint недоступна |
| Лишние поля в payload | глобальный `ValidationPipe`, `whitelist`, `forbidNonWhitelisted` |
| Повторная отправка | `UNIQUE(sender_id, client_message_id)` и возврат существующей записи |
| Удалённый участник остаётся в room | принудительный `socket.leave` для всех его соединений |
| Секрет в репозитории | `JWT_SECRET` только из окружения; `.env.example` содержит шаблон |
| Запрос с чужого origin | CORS по `FRONTEND_ORIGIN` |

## 10. Ограничения модели

- Refresh-токенов нет. После истечения access JWT пользователь входит заново.
- Нет серверного списка отозванных токенов. Выход удаляет токен у текущего клиента, но не отзывает уже скопированную строку.
- Нет MFA, восстановления пароля и подтверждения аккаунта.
- Нет обязательного rate limiting; это возможное развитие, а не реализованная функция.
- HTTPS завершает инфраструктура перед приложением; локальная Docker-демонстрация использует HTTP.
- Роли относятся к конкретному GROUP-чату. Глобальной роли администратора всей системы нет.
