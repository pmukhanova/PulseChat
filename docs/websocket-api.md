# WebSocket API PulseChat

## 1. Транспорт и назначение

PulseChat использует Socket.IO поверх NestJS Gateway. Основной транспорт в браузере - WebSocket; Socket.IO может согласовать polling как технический fallback. Отдельный message broker не используется.

REST отвечает за вход, список чатов, историю, поиск и управление группой. Socket.IO отправляет новые сообщения и лёгкие invalidation-события в персональную room `user:<userId>`, поэтому доставка не зависит от того, открыт ли нужный чат.

По умолчанию клиент подключается к origin страницы. Для отдельного адреса используется `VITE_SOCKET_URL`. Backend ограничивает origin через `FRONTEND_ORIGIN`.

## 2. Подключение и аутентификация

Клиент:

```ts
const socket = io(socketUrl, {
  auth: { token: accessToken },
  transports: ['websocket', 'polling'],
});
```

Токен передаётся без логирования в `handshake.auth.token`. Сервер проверяет подпись, срок и наличие пользователя. При успехе он записывает пользователя в `socket.data` и присоединяет соединение к `user:<userId>`.

При отсутствующем или невалидном токене соединение отклоняется с `connect_error` и текстом `Unauthorized WebSocket connection`.

## 3. Формат подтверждений

Клиент передаёт callback Socket.IO как ack. Общий успешный ответ:

```json
{
  "ok": true
}
```

Ошибка обработчика:

```json
{
  "ok": false,
  "error": "Нет доступа к этому чату"
}
```

Ack `send_message` подтверждает, что сервер обработал запрос и вернул сохранённое сообщение. Это не квитанция о прочтении и не доказательство доставки каждому получателю.

## 4. События клиента

### `join_chat`

Назначение: проверить членство и добавить сокет в комнату активного чата.

Payload:

```json
{
  "chatId": "2cf568be-27d8-42a0-a081-e7a22b06dd44"
}
```

Успешный ack:

```json
{
  "ok": true,
  "chatId": "2cf568be-27d8-42a0-a081-e7a22b06dd44"
}
```

Ошибки: невалидный UUID, чат не существует или пользователь не является участником. Отсутствие членства не раскрывает содержимое чата.

### `leave_chat`

Назначение: удалить текущий сокет из комнаты при переключении диалога.

Payload и успешный ack совпадают по форме с `join_chat`. Событие не удаляет пользователя из `chat_members`.

### `send_message`

Payload:

```json
{
  "chatId": "2cf568be-27d8-42a0-a081-e7a22b06dd44",
  "content": "Привет!",
  "clientMessageId": "7d031d58-c9c8-4d1b-8d51-b4d52d4332ac"
}
```

Ограничения:

- `chatId` и `clientMessageId` - UUID;
- `content` после `trim` - 1-2000 символов;
- лишние поля запрещены;
- отправитель должен состоять в чате.

Gateway преобразует неизвестный payload в DTO и валидирует его внутри обработчика. Поэтому ошибка формата возвращается тем же ack как `{ "ok": false, "error": "..." }`, а клиент не ждёт таймаут из-за отдельного события ошибки.

Успешный ack:

```json
{
  "ok": true,
  "deduplicated": false,
  "message": {
    "id": "0151c0bf-1ad0-4f4e-b591-264ee62f56db",
    "chatId": "2cf568be-27d8-42a0-a081-e7a22b06dd44",
    "content": "Привет!",
    "clientMessageId": "7d031d58-c9c8-4d1b-8d51-b4d52d4332ac",
    "sender": {
      "id": "36cb74bf-dd9b-4e38-af5b-bb5ebd4b1637",
      "username": "andrey"
    },
    "createdAt": "2026-07-11T12:00:00.000Z"
  }
}
```

Алгоритм:

1. Проверить DTO и членство.
2. Найти сообщение по `(sender_id, client_message_id)`.
3. Если записи нет, сохранить её в PostgreSQL и загрузить автора.
4. Только после успешной записи отправить `message_created` в персональную room каждого текущего участника.
5. Вернуть ack отправителю.
6. Если ID уже существует, вернуть существующее сообщение с `deduplicated: true` и не публиковать второе событие.

Если тот же отправитель попытается использовать уже занятый `clientMessageId` для другого `chatId`, сервер возвращает conflict, а не старое сообщение из другого чата.

## 5. События сервера

### `message_created`

Получатели: все подключённые сокеты в персональной room каждого текущего участника, включая отправителя. Получателю не нужно предварительно выполнять `join_chat`.

```json
{
  "id": "0151c0bf-1ad0-4f4e-b591-264ee62f56db",
  "chatId": "2cf568be-27d8-42a0-a081-e7a22b06dd44",
  "content": "Привет!",
  "clientMessageId": "7d031d58-c9c8-4d1b-8d51-b4d52d4332ac",
  "sender": {
    "id": "36cb74bf-dd9b-4e38-af5b-bb5ebd4b1637",
    "username": "andrey"
  },
  "createdAt": "2026-07-11T12:00:00.000Z"
}
```

Клиент объединяет optimistic-сообщение и серверную запись по `clientMessageId`, поэтому собственное сообщение не должно отображаться дважды.

### `chat_list_changed`

Получатели: персональные rooms пользователей, которым стал доступен новый чат. Payload не содержит `Chat`, потому что title DIRECT и `currentUserRole` зависят от получателя.

```json
{
  "chatId": "2cf568be-27d8-42a0-a081-e7a22b06dd44",
  "reason": "CREATED"
}
```

`reason`: `CREATED` или `MEMBER_ADDED`. Клиент тихо обновляет REST-список чатов, не переключая пользователя в новый чат.

### `chat_details_changed`

Получатели: персональные rooms текущих участников GROUP-чата.

```json
{
  "chatId": "2cf568be-27d8-42a0-a081-e7a22b06dd44",
  "reason": "ROLE_CHANGED"
}
```

`reason`: `RENAMED`, `MEMBER_ADDED`, `MEMBER_REMOVED` или `ROLE_CHANGED`. Клиент получает свою актуальную модель через `GET /api/chats/:chatId`, поэтому title, участники и `currentUserRole` корректны для каждого пользователя.

### `chat_access_revoked`

Получатель: персональная комната удалённого пользователя.

```json
{
  "chatId": "2cf568be-27d8-42a0-a081-e7a22b06dd44"
}
```

Перед событием сервер удаляет все активные сокеты пользователя из комнаты чата. Даже если клиент проигнорирует событие, дальнейшие операции защищены проверкой членства.

## 6. Retry и дедупликация

Frontend ждёт ack до 5 секунд. При таймауте и всё ещё активном соединении он выполняет один повтор. Критическое правило: повтор использует тот же payload и точно тот же `clientMessageId`.

```ts
const clientMessageId = crypto.randomUUID();
const payload = { chatId, content, clientMessageId };

await sendOnce(payload).catch(async (error) => {
  if (isAckTimeout(error) && socket.connected) {
    return sendOnce(payload); // ID не меняется
  }
  throw error;
});
```

Если на retry создать новый UUID, сервер воспримет запрос как новое сообщение. Уникальность `(sender_id, client_message_id)` является последней линией защиты от гонки двух одновременных запросов.

## 7. Порядок и восстановление

- Стабильный порядок внутри чата задаётся `(created_at, id)`.
- Событие публикуется после записи, поэтому получатель может сразу найти сообщение в REST-истории.
- После реконнекта клиент повторяет `join_chat` для активного чата и загружает последнюю историю REST. Персональные события не имеют server-side replay; список и история REST остаются источником восстановления после отсутствовавшего соединения.
- Socket.IO room хранится в памяти одного backend-процесса. Это соответствует монолитному MVP.

## 8. Производительность

Слайд кейса формулирует пользовательский ориентир «почти мгновенно», обычно менее 200 мс. Для PulseChat это целевой NFR локального сценария «emit клиента -> серверный ack / событие другого клиента», а не SLA и не уже доказанный показатель. Фактическое измерение должно быть внесено в [testing.md](testing.md) после запуска повторяемого теста.
