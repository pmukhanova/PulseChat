# Сценарий выступления

Каждый блок рассчитан примерно на 35–55 секунд. После слайдов 4, 9 и 12 можно сделать короткую паузу для вопроса аудитории.

## 1. PulseChat

PulseChat — индивидуальный проект по кейсу №1 «Мессенджер». Цель была не в том, чтобы собрать максимально много технологий, а в том, чтобы сделать проверяемый MVP: пользователи регистрируются, общаются в личных и групповых чатах, управляют ролями и видят изменения в реальном времени. В проекте есть backend, frontend, миграции, seed, тесты, Docker и материалы для защиты.

## 2. Обязательный MVP

Из требований я выделил семь опорных функций: регистрация и JWT, DIRECT и GROUP, быстрый обмен сообщениями, история вверх, поиск, роли и real-time. Архитектурные возможности из дополнительного материала не сделали обязательными. Поэтому в MVP есть идемпотентность отправки, но нет Kafka, RabbitMQ, вложений, object storage и server-side read receipts.

## 3. Пользовательский путь

Путь начинается с регистрации или входа. Затем пользователь выбирает существующий чат либо создаёт новый DIRECT или GROUP. Он отправляет сообщение, а другие участники видят его без обновления страницы. В группе права зависят от роли. Важный момент: данные всегда можно заново получить по REST, а Socket.IO только сообщает интерфейсу, что что-то изменилось.

## 4. Интерфейс

Здесь показан реальный интерфейс. Sidebar содержит список чатов, preview последнего сообщения и локальный unread badge. Центральная часть показывает историю и composer. Для администратора появляются действия со списком участников. Этот экран полезен как точка проверки: frontend не просто рисует optimistic-сообщение, а объединяет его с сохранённой серверной записью.

## 5. Архитектура

Это модульный монолит: React-клиент работает через Nginx с одним NestJS backend, а PostgreSQL хранит предметные данные. REST отвечает за запросы состояния: вход, список, детали, историю и поиск. Socket.IO использован для событий реального времени. Отдельный broker или Redis здесь не нужен: один backend-процесс обслуживает персональные Socket.IO rooms.

## 6. Модель данных

В основе пять таблиц. Пользователь и чат образуют N:N через `chat_members`, где одновременно хранится роль. Сообщение связано с чатом и отправителем. Составной ключ membership не допускает двойного участия, а уникальность `(sender_id, client_message_id)` делает повтор отправки безопасным. Индекс истории поддерживает cursor pagination без тяжёлого offset.

## 7. Аутентификация и доступ

Пароль хранится только в bcrypt-хэше. После регистрации или входа клиент получает access JWT: REST передаёт его в Bearer header, Socket.IO — в handshake. Но JWT — только первый барьер. Для чата, истории, поиска и отправки backend всегда отдельно проверяет membership. Для групп дополнительно применяются правила OWNER, ADMIN и MEMBER.

## 8. Отправка сообщения

Последовательность принципиальна: Gateway получает `send_message`, проверяет контекст пользователя и DTO, сервис проверяет membership, затем PostgreSQL сохраняет сообщение. Лишь после этого registry отправляет `message_created` в `user:<participantId>` всех участников, а отправителю возвращается ack. Если ack потерялся, retry с тем же `clientMessageId` возвращает уже существующую запись: второго INSERT и broadcast нет.

## 9. Синхронизация без reload

Персональные rooms решают проблему неактивных чатов. Если один пользователь создаёт DIRECT, второй получает `chat_list_changed` и тихо обновляет список. Новое сообщение обновляет sidebar; для чужого сообщения в неактивном чате увеличивается локальный unread. При смене названия, состава или роли приходит `chat_details_changed`, и frontend запрашивает только нужный чат. После reconnect клиент также тихо обновляет весь sidebar, поэтому новый preview и порядок восстанавливаются без большого spinner и без reload.

## 10. Роли в группе

OWNER — старший администратор и единственный, кто назначает или снимает ADMIN. OWNER и ADMIN добавляют MEMBER. ADMIN не может удалить ADMIN или OWNER, а MEMBER не получает административных кнопок. Это не только условие интерфейса: backend возвращает 403 для запрещённого вызова, поэтому обходить ограничения через HTTP нельзя.

## 11. История и поиск

История идёт по cursor `before`: при нажатии «загрузить ещё» клиент запрашивает только более старую часть и добавляет её сверху. Так интерфейс не зависит от номера страницы и устойчивее к новым сообщениям. Поиск использует `ILIKE` и ограничен одним доступным пользователю чатом. Для учебного объёма это понятное решение; при росте данных нужен отдельный поиск PostgreSQL.

## 12. Проверка качества

Проверки разделены на уровни: lint и build, Docker Compose и healthchecks, миграция на чистой БД, повторный seed, backend e2e/WebSocket и Playwright с двумя контекстами. Backend-набор содержит 21 тест, включая personal rooms, список, роль и идемпотентность. В таблице в документации фиксируются только фактически выполненные команды, без неподтверждённых замеров.

## 13. Границы MVP

Здесь важно назвать ограничения прямо. Нет refresh-token, multi-instance adapter, брокера, вложений, server-side read receipts и формального SLA. Unread — локальный UI-state. Это не скрытый долг, а осознанная граница MVP: сначала измерения и реальные потребности, затем выбор broker, масштабирования или полнотекстового поиска.

## 14. Итог

PulseChat покрывает обязательный сценарий мессенджера и подтверждает его тестами и демонстрацией. Главное техническое решение — доставка сообщений и invalidation через персональные rooms: пользователь получает изменения и в неактивном чате. Следующий шаг для production — измерить нагрузку и задержку, после чего выбирать масштабирование, broker или read receipts на основе фактов.

## 15. Приложение

Если нужен технический разбор, последний слайд показывает полную sequence-диаграмму: проверку membership, поиск по `clientMessageId`, запись в PostgreSQL, доставку в персональные rooms и ack. В основной части оставлен только крупный главный путь, чтобы схема читалась на проекторе.
